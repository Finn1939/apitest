# Capri voice playback investigation — handoff for Astra

## What to investigate

Capri's Discord bot successfully joins voice and produces Fish TTS audio, but listeners report hearing nothing. Independently trace the outbound voice path and identify the most likely failure point. Do not treat generated bytes or `AudioSource.read()` counters as proof that listeners received audible audio. Prefer a minimal, testable fix or the next diagnostic that distinguishes local encoding, UDP transport, and Discord-side mute/permission behavior.

## Project context

Capri is a Discord AI bot with a Node.js bot and a Python `discord.py` voice implementation. The Python voice path uses Gemini Live Transcription for incoming speech and Fish Audio TTS for outgoing speech. Voice data is intended to remain in memory. The related implementation and tests are included in this archive.

## Findings so far

- The current outbound path requests 24 kHz, 16-bit mono PCM from Fish, resamples it to 48 kHz, 16-bit stereo PCM, then feeds a custom `discord.AudioSource` to `discord.py`'s Opus encoder and UDP voice sender.
- A recent `/vc_status` reported `TTS requests/successes: 1/1`, `API audio bytes: 77878`, `Playback frames read: 82`, `Non-silent frames read: 81`, `Buffered: 0 B`, and no TTS error. At 24 kHz mono 16-bit, 77,878 bytes represent about 1.62 seconds; 82 Discord frames represent about 1.64 seconds.
- The corresponding bot log showed a completed Discord voice handshake and successful Fish TTS synthesis. No `discord.voice_client` “A packet has been dropped” DEBUG message or playback callback error appeared. DEBUG logging for that logger is enabled in `python/bot.py`.
- These observations establish that TTS returned data and the local audio player consumed approximately the expected duration. They do **not** prove remote Discord receipt or audibility; Discord voice UDP has no per-audio-packet acknowledgment.
- `discord.py` 2.7.1 catches `OSError` in `VoiceClient.send_audio_packet()` and only emits a DEBUG log. We enabled that logger to surface this failure mode; no dropped-packet message has been observed in the latest attempt.
- The bot reported `Listening: unavailable` in one session and `TTS-only` in another. Runtime import output says `cannot import name 'voice_recv' from 'discord.ext'`. The manifest declares `discord-ext-voice-recv>=0.5.0`, but it was unavailable in the configured environment. This impacts inbound ASR/voice receive and appears separate from outbound TTS.
- The user reports that nobody hears the bot and says Speak permission is allowed and the bot is not server-muted. Effective channel-specific permission overrides have not been independently queried through Discord.
- The non-silent metric currently checks `any(frame)`, not RMS/loudness. It is only a nonzero-byte indicator, not an audibility test.

## Added playback diagnostic

- `/vc_beep` queues a generated two-second, 440 Hz tone at 25% amplitude into the same `VoiceAudioSource` used by Fish TTS. It bypasses Fish, Gemini, and NVIDIA; Capri must already be connected with `/vc_join`.
- `/vc_status` now reports effective Speak permission for the connected voice channel, server mute, self mute, Stage suppression, whether the player is active, playback callback error count and latest error, plus full-sample RMS for the latest audio frame consumed by the player. The RMS is measured across every signed 16-bit PCM sample in that frame; unlike the nonzero-frame count, it indicates signal level but still does not prove remote audibility.
- `discord-ext-voice-recv==0.5.2a179` is now installed in the active `.venv`; `from discord.ext import voice_recv` succeeds. The existing test module now passes (19 tests), including checks for the beep's two-second PCM duration and RMS.
- The previously running bot was stopped and restarted after the code/dependency update. The fresh process (PID 111265) connected to the Discord Gateway without the prior voice-receiver import warning.

## Next test

1. Run `/vc_join` and `/vc_status`. Confirm voice receive is installed and note permission/mute/Stage state.
2. Run `/vc_beep` and listen from another account/client if possible. Check `/vc_status` for `Playing`, `Last-frame PCM RMS`, and playback errors.
3. If the beep is audible but Fish speech is not, inspect Fish PCM format and measured PCM level. If both are silent, investigate effective Discord permissions, mute/Stage suppression, DAVE/voice encryption, and UDP delivery. If both are audible, test ASR separately.

## Prior research

- [Gopher voice chat source](https://github.com/bas3line/Gopher/blob/main/src/voice/chat.ts) uses `@discordjs/voice`, an Ogg Opus resource, and explicit player idle/error handling. This is a useful comparison, not proof that its approach fixes Capri.
- [TomoriBot](https://github.com/Bredrumb/TomoriBot) is a self-hosted Discord AI companion with personas, tools, memory, and voice features; its public docs emphasize voice messages/speech integrations more than this exact Python live-channel path.
- [Project Gabriel](https://github.com/HoppouAI/ProjectGabriel-Remastered) is a Gemini Live voice companion with a Discord integration, but its main voice use case is VRChat/local audio routing.
- [AstrBot](https://github.com/AstrBotDevs/AstrBot) is a multi-platform agent/chatbot framework with Discord, plugins, and multiple ASR/TTS integrations.
- [llmcord](https://github.com/jakobdylanc/llmcord) is a lightweight Discord frontend for hosted/local LLMs and is not a close live-voice/server-actions analogue.
